## P0 — blocking (must resolve before commit)

### P0-1. `.env:2` — the temporary ceiling override sits in a **tracked** file
`.env` is tracked in this repo (it appears in `git diff`), so committing the current worktree ships `FOUNDRY_CLUSTER_POLL_CEILING_MS=8000` as the repository default. Every real cluster run in every clone would hit the poll ceiling after **8 seconds** and permanently lean on the SSE handoff (which is itself capped at 2h) instead of the intended 30/120-min ceilings — precisely the "ceiling lies" failure mode this lane spent two tasks eliminating.

**Fix:** remove the line before commit. For the dev-server-side override the runbook itself needs, point `docs/CONTRIBUTING.md:118` at **`.env.local`** instead of `>> .env`: `.env.local` is already gitignored (`.gitignore:34`, verified with `git check-ignore`) and Next.js gives it higher precedence than `.env`. Also note the currently-running dev server still carries the 8s ceiling — after removing the line, the runbook's restart step (daemon-run.py) is what actually restores the default.

## P1 — should fix

### P1-1. `cluster-run.ts:690-704 + 841-856` — applySweepBlock's terminal-state guard reads a STALE run snapshot; an in-flight sweep can still clobber a just-stopped ToolJob row (zombie "running" row + lost via-node-stop badge)
The 30-b fix guards `applySweepBlock` with `run.phase` — but `run` is the object captured by `doSweep`'s `listRuns()` **at sweep start**, and `updateRun()` (cluster-run.ts:93-101) *replaces* the map entry with a new object, so the sweep's array keeps the old reference. `stopClusterJob` (cluster-run.ts:948-1006) runs **outside** the `sweepInFlight` guard: while it is doing its remote-kill SSH round trips (1-20s), a sweep that started seconds earlier still sees `phase:"running"`:
- ALIVE branch (841-856) → `updateJobRow(jobId, { status: "running", stdout, stderr })` — an **unconditional** `db.toolJob.update` that overwrites the row `stopClusterJob` just flipped to `cancelled` (single-point write + `[stop] cancelled via node stop` marker, both lost);
- EXIT-n≠0 / vanished branches (795-835) can likewise flip a cancelled row to `failed`.

After the clobber, the run *record* says `cancelled` (merged correctly — `updateRun` merges onto the live entry), so the record is filtered out of future sweeps and **nothing ever re-settles the DB row** — the jobs UI shows a job "running" forever. This is the exact class 30-a flagged; the entry guard closed the *fresh-sweep* window but not the *in-flight* window (up to the 25s `execRaw` timeout).

**Why this diff matters:** the new stream co-driver (`stream/route.ts:208-222`) fires `reconcileClusterJobs()` every ~3s while any stream watches a marker-bearing running node — i.e. the inspector stream is open exactly when a user hits Stop in the Runs sheet. Combined with the run lane's own 3s sweeps, the in-flight overlap probability during a stop goes from "occasional" to "likely on real SSH" (sweep exec ~1-3s vs 3s cadence). The P3 e2e path itself can flake on this (run-lane sweep in flight during the stop).

**Fix (two lines of defense):**
1. Re-read the live phase at entry: `const live = getRun(run.jobId); const phase = live?.phase ?? run.phase;` and guard on `phase` (also covers the EXIT-0 `run.phase === "syncing"` check at :787).
2. Make the row writes conditional, mirroring the Node-lane discipline: the ALIVE write → `db.toolJob.updateMany({ where: { id, status: { notIn: ["completed","failed","cancelled"] } }, data })`; same for the EXIT/vanished writes (`where: { id, status: "running" }`). This also protects against the `jobs/:id/stop` route's write racing a sweep.

### P1-2. `mini-services/mock-cluster/index.ts:1502` + `shims/sched-client.ts:26,31` — 3 NEW `tsc --noEmit` errors; repo-wide verification gate regressed 4→7
The new loopback code is the first `Bun`-global reference in the file (verified: zero `Bun.` refs at HEAD), producing `TS2867: Cannot find name 'Bun'`; and `sched-client.ts` uses top-level `await` with no import/export, producing two `TS1375` errors (script, not module). Both files *run* fine under the Bun runtime, but the project's standing gate ("tsc clean except the 4 pre-existing examples/skills errors") now fails repo-wide, and the worklog claims ("tsc 零错误，4 条预存 examples/skills") become false if stated for the whole repo rather than `src/`+`scripts/`.

**Fix:** add `export {}` to `shims/sched-client.ts` (module marker, kills both TS1375s); in `index.ts` either add a minimal ambient `declare const Bun: { serve: (o: Record<string, unknown>) => { stop: (f?: boolean) => void } }`, or route through `(globalThis as { Bun?: ... }).Bun?.serve` with a fallback log. (Alternatively exclude `mini-services` from tsconfig — but the existing mock code already type-checks, so the two one-liners are cheaper.)

## P2 — nice / hardening

### P2-1. `node-group.tsx:336-351` — the pointerdown claim is **VERIFIED**; trade-offs declared but worth an alternative
Verified against `workflow-canvas.tsx`: `isBackground` (432-440) has no carve-out for group frames (no `data-node-card`/`data-port`/`data-create-menu`), so the section's `onPointerDown` captured the pointer (453) and retargeted pointerup+click to the section; `setActiveGroup`'s **only** caller is the frame's onClick (node-group.tsx:354) — i.e. before this fix, group selection and the × button were dead code in real browsers (JS `click()` in e2e could not have caught this — consistent with the project's real-pointer rule). The same stopPropagation pattern is already precedented by the create-menu and group-prompt click-away catchers (workflow-canvas.tsx:905, 969). Net: the fix is correct and necessary.
Trade-offs (as declared in the comment): pan can no longer start on a frame, and shift+band-select can no longer *start* on a frame. Task 31's e2e-verified band-select started on empty canvas → unaffected; band drag that *crosses* frames still works (capture was set at pointerdown on the section). **Suggested alternative** (equivalent effect, less global): give frames a `data-group-frame` attribute and make `isBackground` return `false` for it — the section handler then early-returns without suppressing propagation for any other ancestor; today there are no other ancestors, so both are fine — file under consistency.

### P2-2. `node-group.tsx:429-528` — double-click inside the editor's label input opens the canvas create-menu popover
`onDoubleClick` on the section (workflow-canvas.tsx:537) treats the editor input as background (`isBackground` → true), so a word-select double-click in the group label input opens the create-node popover *over* the editor; the popover's fixed inset-0 click-away catcher then swallows the user's next pointerdown (905-908). Pre-existing pattern (the NodeSearch input and the Ctrl+G prompt input share it), but the editor is new exposure with a focused text field where double-click-to-select-word is a normal gesture. **Fix:** `onDoubleClick={(e) => e.stopPropagation()}` on the editor panel (or teach `isBackground` to skip `[data-group-editor]`/`input`).

### P2-3. `node-group.tsx:255-296` — ghost frame geometry edge cases (cosmetic)
(a) A user group whose members span **two** sweep aggregates (two sweeps' variants grouped together) renders one ghost at the global member min — it no longer hugs either aggregate card, it straddles the region between them. (b) Mid-E3-drag: the aggregate card visually translates while the ghost stays put until the drop commits member coords (then both jump together) — acceptable cosmetic lag. (c) Narrow edge: if a sweep group shrinks below 2 members (member deleted) while `collapsedSweepGroups` still holds its id, `deriveSweepGroups` drops it (no aggregate card — canvas renders the lone member as a normal card), but node-group's `visible` filter (:244-246) still counts that member as folded → an allFolded ghost renders *behind a real card* with a "1 folded" label that lies. **Fix (c):** align the fold test with `deriveSweepGroups` semantics (a member is folded only if its sweep group has ≥2 live members), or accept and document.

### P2-4. `node-group.tsx` frames — no keyboard path to group selection

### P2-5. `mini-services/mock-cluster/index.ts:1488-1529` — fixed port 3023: an EADDRINUSE throw at module top level kills the whole mock-cluster
`Bun.serve` throws synchronously when :3023 is occupied; this code runs *after* `server.listen(3022)`, so a port squatter crashes the SSH server too, with a stack trace instead of a harness-legible message. **Fix:** wrap in try/catch and `log()` "sched loopback unavailable (port 3023 in use) — scheduler file shims degraded"; shims then fail with exit 126 (`sched-client.ts:29`) which is an honest, debuggable signal.

### P2-6. `scripts/e2e/cluster-lane.ts:387-396` — P3's waitFor timeout is honest but not *diagnostic*
If the dev server lacks the env var, P3 times out with `timeout waiting for node running + poll-ceiling marker in logs` — technically honest, but the most likely cause (server env ≠ `--ceiling` declaration) is not named, and CONTRIBUTING sells this as "明确错误". **Fix:** catch the waitFor timeout and rethrow with `dev server may lack FOUNDRY_CLUSTER_POLL_CEILING_MS=${CEILING_MS} (declared via --ceiling) — restart it per CONTRIBUTING before rerunning`.

### P2-7. `scripts/e2e/cluster-lane.ts` (P1/P6) — crashed-run leftovers are detected but never self-healed
P1's idempotent preflight cleans stale *connections* by name only. A crashed run (process kill, or the P3-timeout scenario above) leaks: the `WF_NAME` workflow (P2 creates a second one with the same name on rerun), its nodes (they cascade only when the workflow is deleted), ToolJob rows, run records, and `outputs/rfdiffusion/*`. The final baseline-count assertions *catch* the drift (honest failure) but a rerun never converges. **Fix:** in P0/P1 preflight, also delete any workflow named `WF_NAME` (cascade cleans nodes) and delete ToolJobs created after the baseline snapshot (e.g. `where: { createdAt: { gt: baselineAt } }` scoped to the rfdiffusion/cluster tools) — or at minimum the WF_NAME workflow.

### P2-8. `scripts/e2e/cluster-lane.ts:653-654` — P6 deletes the whole `outputs/rfdiffusion` tree

### P2-9. `cluster-run.ts:753` — real `sacct` "CANCELLED by <uid>" states fall through to "vanished"
