## P1 — should fix this round

### P1-1 — Stale `STOP_REQUESTED` flag poisons the NEXT run of a stopped node
**File**: `src/lib/node-run-control.ts:29-41` (registry), `:120-128` (only consumer/cleaner), `:150` (writer).
**What breaks**: `stopNodeRun` calls `requestStop(nodeId)` first. The flag is consumed *only* by `executeNodeGuarded`'s post-race check (`isStopRequested` → `clearStop`). For a **poll-ceiling cluster node** (row "running", execution lane already exited at the poll ceiling, only the SSE reconciler owns it) there is **no in-flight guard** — so every stop of such a node leaves the flag permanently set. The next run of that node (reclaimer accepts `cancelled`) executes the node **fully** (potentially minutes of real compute), then the guard sees the stale stop and returns `cancelled`. The user re-runs a stopped node and gets "Stopped by user" *after* paying for the whole execution. The same happens in the sub-ms gap between the guard's check and the runner's status write for local nodes (rare), and for a stop that lands after a lane just finished (row still "running" briefly).
**Why**: single writer (`requestStop`) with a single consumer that only runs while a guard is in flight.
**Fix** (pick one, ideally the first):
1. `executeNodeGuarded` calls `clearStop(node.id)` **at entry** — each fresh execution discards stale flags before doing work (stops registered *during* execution are still honored by the post-race check — semantics unchanged).
2. Additionally, `stopNodeRun` can skip `requestStop` when it can see no in-flight lane (e.g. only flip the row for poll-ceiling rows) — harder to detect; option 1 is sufficient.

### P1-2 — Stop vs. stream-reconcile race: stopped cluster node can land **failed** (or be resurrected to **running**)
**Files**: `src/lib/node-run-control.ts:149-190` (stopNodeRun order), `src/app/api/workflow/nodes/[id]/stream/route.ts:144` (mapping), `src/app/api/workflow/nodes/[id]/run/route.ts:140-147` + `src/lib/workflow-runner.ts:187-196` (running-branch writes).
**What breaks** (two coupled defects):
1. `stopNodeRun` runs `requestStop → killActiveProcess → stopClusterJob (await, can take seconds) → row flip`. In the window between the cluster job being marked `cancelled` and the row flip, the node is still `"running"` and its logs carry the `[cluster run · job …]` marker — so an open SSE stream's 500ms poll (`reconcileClusterOutcome`) fires, sees `job.status === "cancelled"`, and — because line 144 maps **anything not completed → `"failed"`** — writes `status: "failed"` + `completedAt`. The stop's subsequent `updateMany` (`where status in running/pending`) then matches 0 rows: **the user pressed Stop and got a red FAILED node** (plus the P1-1 stale flag). Realistic flow: watch a cluster node in the inspector, hit Stop on its card.
2. The sub-ms gap: guard's `isStopRequested` check passes (no stop yet) → outcome `"running"` (poll ceiling) → `runOne`/`runNode`'s `if (status === "running")` write lands *after* `stopNodeRun`'s flip → row overwritten **running**, cluster job already cancelled, node wedged "running" until the 2h stream cap / boot reconcile. (Answering question 7a directly: in the *normal* path the guard returns `cancelled`, the `running` branch is skipped and the final write re-persists `cancelled` — cancelled IS preserved; only this gap can resurrect `running`.)
**Fix bundle**:
1. `stream/route.ts:144`: map `job.status === "cancelled" → "cancelled"` (node status), keeping `failed` for `failed`.
2. `stopNodeRun`: flip the row (`updateMany`) **before** the (slow) cluster cancel + process kill, so the reconciler (which only acts on `"running"` rows) can no longer race it.
3. (Belt-and-braces) In the `status === "running"` branches of `runOne`/`runNode`, write with `where: { id, status: "running" }` (`updateMany`) so a terminal row is never overwritten by a late lane.

### P1-3 — Stream chat lane records the *deferred* compute skill as a `failed` ToolCall
**File**: `src/app/api/agents/[id]/chat/stream/route.ts:180-193`; rendered in `src/components/panels/agent-chat-drawer.tsx:417-437`.
**What breaks**: the old code pushed only a follow-up note (no ToolCall) for comp tools in the streaming lane. The new code records `status: "failed"` with result "Deferred: …". `ToolCallCard` renders `failed` as a **rose "FAILED" pill** — the user sees a red failure card for something that did not fail (it was deferred to the canvas by design). Honesty regression in the visible transcript.
**Fix**: add `"deferred"` to `ToolCall["status"]` (`src/lib/types.ts:70`) and render a neutral/slate pill in `ToolCallCard` (one more ternary); or, minimal, omit `status` for the deferral row (the pill is conditionally rendered on `call.status`).
**Also note (positive)**: recording a card at all is an improvement over the old invisible deferral — the model's instruction to use the canvas is now visible; only the *status* is wrong.

### P1-4 — RunsSheet Row keyboard: Enter/Space on the inner Stop (and Retry) button triggers the row jump instead
**File**: `src/components/panels/runs-sheet.tsx:106-117` (Row), Stop button `:447-463`, Retry (pre-existing, same flaw).
**What breaks**: the Row root is `div[role=button]` with `onKeyDown` that handles Enter/Space unconditionally. A keydown on the inner `<Button>` **bubbles** to the Row: the Row's handler calls `preventDefault()` (canceling the button's default activation) and runs `onClick` (jump-to-canvas). A keyboard user who tabs to the Stop button and presses Enter gets a canvas navigation, **not a stop**. Mouse users are unaffected (`stopPropagation` on click).
**Fix**: at the top of the Row `onKeyDown`: `if ((e.target as HTMLElement).closest("button, a, [role='button']")) return;` (or `if (e.target !== e.currentTarget) return;`).

## P2 — note for roadmap / small cleanups

1. **E1 watchdog timer leak** — `src/lib/node-run-control.ts:94-99`: the `Promise.race` timeout `setTimeout` handle is never stored/cleared and is not `.unref()`'d. Every *completed* node run leaves a live timer for the full budget (**15 min default, 35 min cluster, 125 min alphafold-cluster**), holding the reject closure (~small) and keeping the event loop hot. The later reject on the settled race is harmless (race attached handlers → no unhandledRejection). Not a correctness break, but it contradicts the executor's own pattern (`executor.ts` clears in `finally`) and accumulates over a long session. Fix: `let timer; try { … } finally { clearTimeout(timer) }` (mirror executor.ts) or `.unref()`. (This answers question 6: the *skill* executor has **no** leak — its `finally` clears the timer whichever promise wins; the *node* watchdog does.)
